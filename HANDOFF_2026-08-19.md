Written 2026-08-19 by the Claude Code session working in the dbt/Neon repo on
the Mac side, for whoever picks this up next (Windows Claude Code + PBI MCP).
Everything below is fact, not speculation, unless marked otherwise.

## The immediate blocker

Refreshing the model now throws:

```
4 queries are blocked by the following error:
fct_klant_product
A cyclic reference was encountered during evaluation.
```

"Blocked" (not "failed") on the other 3 — Power BI's refresh dialog uses that
word for queries skipped when the refresh transaction aborts, so there is
almost certainly **one real error**, on `fct_klant_product`, and the other 3
are collateral.

**Already ruled out**, from the Mac side, working from the TMDL files only
(no live model access there):

- **Not the M/data-extraction layer.** "Refresh Preview" on `fct_klant_product`
  in Power Query Editor loads fine in isolation — confirmed by the user.
- **Not row-level security.** No `roles.tmdl` or any RLS definitions exist in
  this model at all — checked, none.
- **Not a self-contained calculated-column cycle.** `fct_klant_product` has
  exactly two calculated columns, both fully self-contained:
  ```
  column klant_label =
          VAR Naam = fct_klant_product[klant_naam]
          VAR AantalIds =
              CALCULATE(
                  DISTINCTCOUNT(fct_klant_product[klant_id]),
                  ALLEXCEPT(fct_klant_product, fct_klant_product[klant_naam])
              )
          RETURN IF(AantalIds > 1, Naam & " (" & fct_klant_product[klant_id] & ")", Naam)

  column is_zakelijk =
          VAR B = fct_klant_product[branche]
          RETURN IF(ISBLANK(B) || B = "Consument", 0, 1)
  ```
  Neither references any other table.
- **The visible cross-table calculated-column dependencies are one-directional
  into `fct_klant_product`, not out of it** — traced by hand from the TMDL:
  - `fct_klant`'s `signaal_kleur` / `signaal_tekstkleur` / `risico_kleur` read
    `fct_klant_product[klant_id]` / `[regelstatus]` (plain source columns).
  - `fct_voorraad`'s `omzet_vorige_12m` / `flessen_vorige_12m` /
    `klanten_vorige_12m` / `klanten_nu_zakelijk` read `fct_klant_product`'s
    `product_id` / `omzet_vorige_12m` / `flessen_vorige_12m` / `is_zakelijk` /
    `omzet_12m` (again, plain source columns).
  - Nothing in `fct_klant_product` reads back from either table.
  - By hand this is a DAG, not a cycle — but this is static reading, not the
    Tabular engine's actual resolved dependency graph.

**What's needed next**: something that can see the Tabular engine's real
dependency graph (Tabular Editor's dependency view, DAX Studio, or the PBI MCP
tooling) or bisection (disable calculated columns one at a time, re-refresh,
see when it clears). `model.tmdl`'s own annotations list `"MCP-PBIModeling"`
as a tool already used on this project — that's the live capability the Mac
side doesn't have.

One more lead worth checking first, cheap: `model.tmdl` has an explicit
`PBI_QueryOrder` annotation —
`["dim_customer","dim_date","dim_product","fct_sales","fct_voorraad","fct_klant","fct_klant_product"]`.
Not touched today, but worth confirming it's still being honoured / isn't
itself now contradicted by something in the refreshed dependency graph.

## Why two Claude Code sessions, and the fuller story of today

**Why two sessions.** The dbt/dlt/Neon repo lives on the Mac; Power BI Desktop
is Windows-only, so it runs in a Parallels VM on the same machine, with its
own Claude Code + PBI MCP setup. The Mac session has the full history of every
decision in this project (documented in the repo's `CLAUDE.md`) but can only
reach the PBI project files through a mounted SMB share — no live model
access, no MCP, no way to actually run PBI Desktop. The Windows session has
the reverse: real tooling against the live model, no memory of anything that
happened on the Mac side. This handoff exists to close that gap in one
direction; if useful, the reverse (a summary of PBI-side findings for the Mac
session) is worth doing too.

**The fuller story of today**, not just the PBI repointing:

1. **Read-only access to the ERP's actual database arrived.** Until today,
   this whole platform's only data source was scraping the ERP's website
   (`ingestion/source.py` — HTML parsing, one HTTP fetch per customer/order,
   fragile by construction). The ERP developer granted a MariaDB user this
   morning, firewalled to one specific IP address rather than open to the
   internet (a static egress IP allocated on the `wijngalerij-pipeline` Fly.io
   app specifically for this).
2. **Built a second dlt source reading that database directly**
   (`ingestion/source_db.py`) — reflects ~26 relevant ERP tables (excluding
   backups, CMS content, empty tables) straight off their native schema, real
   types throughout, no HTML parsing. Landed under the tables' own ERP names
   in the same `raw` Postgres schema the scraper already writes to, alongside
   it rather than replacing it.
3. **Found and fixed several real bugs along the way**, not just built happy
   path: MySQL's `'0000-00-00'` zero-date sentinel colliding with inherited
   `NOT NULL` constraints; a subtle Jinja loop-scoping bug that silently
   no-op'd an HTML-entity-decoding macro; a genuinely double-encoded source
   value (`Tard&amp;iacute;o` for what should render as `Tardío`); and a
   9-day-old, currently-still-live bug in the *scraper's* stock-page parsing
   (unrelated to any of this — found only because validating the new
   pipeline's numbers required a working scraper snapshot to compare against).
4. **Built the full dbt staging + mart layer on top of the new tables** — 8
   staging models, then all 7 marts (`dim_product_db` through
   `fct_klant_product_db`), deliberately mirroring the old scraper-sourced
   marts' column names and shapes wherever the underlying data actually
   supports it, specifically so a future Power BI repoint would be close to a
   pure "change the source table name" operation rather than a rewrite. That
   bet mostly paid off today — 5 of 7 tables repointed with no DAX changes at
   all, one bug found in a measure that predates today.
5. **Investigated and resolved a real stock-reconciliation mystery**: summing
   the ERP's stock-mutation ledger looked wrong against the scraper's
   known-good current-stock figures (only 429/736 products matching exactly)
   until the scraper snapshot's actual age (13 days stale) was accounted for —
   once compared at the correct point in time, every product reconciled
   exactly. `voorraad` is trustworthy as a result; `gereserveerd`/
   `in_bestelling` still are not, for reasons in "Known, deliberate gaps"
   below.
6. **Wired the new pipeline into the existing Fly.io-hosted schedule**
   alongside the scraper — the scraper+dbt build still runs once daily at
   06:00 (nothing currently needs it fresher; the Power BI reports it feeds
   are being retired), while the new ERP-database pull now runs hourly,
   07:00–19:00, deliberately more conservative than the ~30-minute ceiling
   Neon's free tier allows, since nothing was yet consuming that cadence.
   Mechanism: `scripts/scheduler.py`, `PIPELINE_MODE=full` vs `PIPELINE_MODE=db`
   passed to `scripts/run_pipeline.sh` depending on which scheduled time fired.
7. **Only then** did today's work turn to Power BI specifically — repointing
   this semantic model onto the new hourly-refreshed marts, which is where
   the rest of this document picks up.

## What changed today, exactly

**Context**: this project has TWO parallel sets of dbt marts in the same Neon
Postgres warehouse (`marts` schema), reachable from the same connection the
model already uses (`ep-soft-salad-agt3f5p2.c-2.eu-central-1.aws.neon.tech`,
role `bi_readonly`, already granted on both sets — verified, no grant work
needed):

- **Old, scraper-sourced marts** (`dim_customer`, `dim_product`, `fct_sales`,
  `fct_voorraad`, `fct_klant`, `fct_klant_product`, `dim_date`) — built from
  HTML-scraping the ERP's web app. Still the only thing some tables in this
  model read from (see below). Refreshes once/day.
- **New, DB-sourced marts**, same names with a `_db` suffix (`dim_customer_db`,
  `fct_sales_db`, etc.) — built from a direct read-only MariaDB connection to
  the ERP's actual database, landed via dlt, transformed via dbt. Refreshes
  hourly, 07:00–19:00 (`scripts/scheduler.py` in the repo). Real typed columns
  throughout, no more scraped-string parsing, and genuinely new data the
  scraper never had (grape/region/vintage, real `product_id` foreign keys —
  0 unmatched order lines vs. the scraper's ~5% fuzzy-name-match failures).

Today's task: repoint this semantic model onto the `_db` marts so its
refreshes pick up hourly-fresh data instead of once-daily.

**Repointed** (M partition source table changed, nothing else, in each
table's `.tmdl` under `definition/tables/`):

| Table | Old source | New source |
|---|---|---|
| `dim_customer` | `dim_customer` | `dim_customer_db` |
| `dim_date` | `dim_date` | `dim_date_db` |
| `fct_sales` | `fct_sales` | `fct_sales_db` |
| `fct_klant` | `fct_klant` | `fct_klant_db` |
| `fct_klant_product` | `fct_klant_product` | `fct_klant_product_db` |

**Deliberately NOT repointed** — `dim_product` and `fct_voorraad` are still
reading the OLD scraper-sourced marts. Reason: the DB-sourced `product` table
has no stock-quantity column of its own, and deriving current stock from the
DB source's stock-mutation ledger (`product_voorraad`) was tested and ruled
unreliable for `gereserveerd`/`in_bestelling` specifically — see "Known,
deliberate gaps" below. Repointing these two now would break every stock/cover
visual. Do not repoint without resolving that first.

**Compatibility casts added** because the two halves of the model (repointed
vs. not) now disagree on `product_id`'s type — DB-sourced marts have real
`bigint` product IDs, the untouched scraper-sourced `dim_product`/`fct_voorraad`
still have string ones. Without a cast, the `fct_sales → dim_product`
relationship and several DAX measures that compare `fct_klant_product[product_id]`
directly against `fct_voorraad[product_id]` (no formal relationship there,
just DAX-level equality) would silently match nothing. Added identical
`Table.TransformColumnTypes(#"Navigation 1", {{"product_id", type text}})`
steps to both `fct_sales.tmdl` and `fct_klant_product.tmdl`'s M partitions,
each commented as removable once `dim_product`/`fct_voorraad` also move over.

**One bug found and fixed today, after the repoint**: `fct_sales`'s
table-level `Omzet` measure (`SUM(fct_sales[regel_totaal])`, defined directly
on the table, not in `_Metingen`) broke because the new `fct_sales_db`'s
equivalent column is named `regel_totaal_bruto` (deliberately — it's
pre-discount, see dbt model comment). This measure is depended on by `Omzet
YTD`, the monthly revenue chart (`Dit jaar`/`Vorig jaar` are aliases of
`[Omzet]`/`[Omzet vorig jaar]`), `Gem. orderwaarde`, `Omzet groei %`, and
`Brutomarge 12m`'s subtitle — explains why those specific tiles broke while
`Orders`/`Flessen`/the banner text (which don't touch `[Omzet]`) kept working.
**Fixed on the dbt side, not in PBI**: added `regel_totaal` back as a plain
alias of `regel_totaal_bruto` in `fct_sales_db` (same value, old name), so the
existing unmodified DAX measure just works again. Already rebuilt and verified
on both Neon branches (`dev` and `prod`) — confirmed `regel_totaal =
regel_totaal_bruto` exactly, 28,431 rows.

## Known, deliberate gaps between the two mart sets

Full inventory is in the dbt repo's conversation history, but the parts that
matter for PBI work:

- **`dim_product_db`/`fct_voorraad_db` have NO stock quantities at all**
  (`voorraad`, `gereserveerd`, `in_bestelling`, `effectieve_voorraad`,
  `dekking_weken`, `voorraadstatus`, `verwachte_uitverkoopdatum` — none of it).
  `voorraad` alone was derived and *verified* correct (matched the scraper's
  known-good figure exactly once compared at the right point in time), but
  `gereserveerd`/`in_bestelling` require a working scraper snapshot to
  validate against, and **the scraper's stock-page parsing has been silently
  broken since 2026-08-11** (returns NULL for `voorraad` on every run since,
  confirmed via `raw.stock_snapshot`'s history on `prod`) — a real, separate,
  currently-live bug, unrelated to any of today's work, not yet fixed.
- `schapvoorraad`, `voorraadwaarde_erp`, `afbeelding_url`/`heeft_foto` don't
  exist in the DB source at all (not "not yet built" — genuinely absent from
  the ERP's database in any form found so far).
- `fct_sales_db` is missing `line_idx` (has `regel_id` instead — a different
  concept, the order line's own primary key rather than a per-order array
  index) and `magazijn` (has `magazijn_id`, unresolved — the `magazijn`
  reference table has only 1 row in the whole ERP, so resolving it is low
  value). Neither is aliased/patched — check if any visual (not measure)
  binds to them directly before assuming they're safe to ignore.
- `product_naam`, `order_type`, `product_naam_ambiguous` ARE patched back onto
  `fct_sales_db` for compatibility (joined from `dim_product_db`, derived from
  `is_sample`, and hardcoded `false` respectively — the ambiguous-name failure
  mode literally cannot happen with a real FK).
- `accountmanager` on `dim_customer_db`/`fct_klant_db` now resolves to a real
  name (added today) via a new `stg_users_cms_db` model — reads the ERP's
  staff-login table but **column-restricted at extraction** to just
  id/username/voornaam/tussenvoegsel/achternaam; the password hash, private
  email/phone, home address and birthdate are never pulled into the warehouse
  at all (see `ingestion/source_db.py`'s `USERS_CMS_COLUMNS`).
- `extracted_at` was missing from `dim_product_db`/`dim_customer_db`/
  `fct_sales_db` and has been added (derived from dlt's own load timestamp,
  not a new column at the source). `fct_voorraad`/`fct_klant`/
  `fct_klant_product` never had this column even in the old marts — confirmed
  by grep, not assumed.
- `order.status_id` (used for `is_verkocht`/order status generally) has no
  lookup table anywhere in the ERP's schema. The mapping used is INFERRED —
  cross-referenced against the scraper's text status for the same orders,
  ~99%+ match rate — and flagged as such in the dbt model
  (`stg_orders_db.sql`). Treat as provisional, not documented fact.
- `fct_klant_product_db`'s `b_wijnkaart` is a real column (from `product_prijs`),
  unlike the scraper-sourced version's own "UNVALIDATED" one — but it has NOT
  been re-checked against the business's own wijnkaart list the way the
  scraper's version was (which disagreed on ~half of matched wines). Don't
  upgrade it from "real column" to "trustworthy" without doing that check.

## Also worth knowing, unrelated to the immediate bug

- **`_Metingen`'s `Prognose omzet jaar` and its ~6 dependent measures are a
  real revenue forecast** (YTD growth × prior year's seasonal shape) reaching
  the CEO dashboard. The dbt repo's CLAUDE.md is explicit: *"No forecasts in
  v1... until forecast-versus-actual reporting exists."* This isn't the same
  thing that rule was written about, but it's a forecast in front of a CEO
  without that tracking in place. Worth a conscious decision, not silence.
- Two stray unnamed measures on `fct_klant.tmdl` (`Measure`, `Measure 2`) —
  harmless leftover clicks, trivial cleanup whenever convenient.
